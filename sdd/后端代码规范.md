## 后端项目结构

以下内容以 **标准 Maven Spring Boot** 为背景；**路径为规划示意**（依据用户澄清「后端将迁入本仓」）。

```text
<backend-root>/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── <根包>/          # 如 com.insigma.xxx — 最终以立项包名为准
│   │   │       ├── …Application.java    # Spring Boot 启动类
│   │   │       ├── config/      # 全局配置
│   │   │       ├── sys/         # 系统域（与用户选定分层一致时可保留）
│   │   │       └── business/    # 业务域，按子模块分子包
│   │   └── resources/
│   │       ├── application.yml
│   │       ├── application-*.yml
│   │       └── mapper/           # 自定义 Mapper XML（若仍使用 XML）
│   └── test/java/
└── target/
```

历史规范中的包划分示例：**根据 `bak/_sdd/spec/04_后端代码规范/后端项目结构.md`**，常见为 `sys`（系统）、`business`（业务）、`config`（全局）。

## 分层结构

自上而下：**应用层（Controller）→ 服务层（Service）→ 数据访问层（Mapper）**，底层由框架与通用组件构成（配置、工具、异常封装等）。

- **Controller**：接收 HTTP，参数校验与装配，调用 Service；**不写业务规则**。
- **Service**：事务与业务编排；返回值 **不使用** `ResponseMessage`（与 Controller 的职责分离）。
- **Mapper**：与数据库交互；优先 MyBatis-Plus API，必要时自定义 SQL/XML。

依赖方向：Controller → Service → Mapper；工具与配置可被上层依赖，避免 Mapper 反向依赖 Service。

**依据**：`bak/_sdd/spec/04_后端代码规范/分层结构.md`（叙述已压缩）。

## Controller层规范

- **瘦身**：只做协议适配、校验触发、权限注解（若有）、调用 Service、`ResponseMessage` 封装。
- **禁止 Swagger 注解**作为接口契约来源（历史规范明文禁止；若团队引入 OpenAPI 代码生成另有流程，须在立项时单列，**不得以注解替代 DTO**）。
- **禁止**使用 `JSONObject`、`Map<String,Object>` 等模糊类型作为 **`@RequestBody` 或多参数主体**；须使用 **`…DTO`** 后缀的请求类。
- **`@RequestMapping` 路径**：
  - 使用 **camelCase**，结构建议 `/{模块类型}/{模块名}/{功能名}`，如 `/business/order/orderManage`、`/sys/user`。
  - **须与前端路由路径一致**（历史规范）。
- **返回**：统一 **`ResponseMessage`**，**不写方法级泛型**（参见「统一响应与核心对象」章）。
- **异常**：一般不在 Controller `try/catch` 业务异常，交给全局异常处理器；极特殊场景若捕获，异常栈须 **`log.error` 级别**记录（可与 Lombok `@Slf4j` 合用）。

**依据**：`bak/_sdd/spec/04_后端代码规范/Controller层规范.md`。

## Service层规范

- 需在方法级判断是否加 **`@Transactional`**（读写、原子性要求高时）。
- **返回类型**：为领域对象、分页结果、`boolean`、`void` 等 **业务语义类型**；不要直接返回 **`ResponseMessage`**（由 Controller 包装）。

**依据**：`bak/_sdd/spec/04_后端代码规范/Service 层规范.md`。

## 数据访问层规范

- Mapper 接口使用 **`@Mapper`**（`org.apache.ibatis.annotations.Mapper`），由 Spring Scan 纳入容器。
- 若沿用历史 **项目封装**：Mapper 继承带 MP 扩展的基接口（历史中示例为 **`BaseDAO<T>`**，包路径形如 `com.insigma.framework.persistence.mybatis.plus.BaseDAO`）。**实际基类名称与包路径以 Starter 源码为准**，落地后请把真实 import 记入团队 Wiki 并回填本文本节。
- 优先 **`lambdaQuery()` / `lambdaUpdate()`**、分页 `page(Page, Wrapper)`、`list`/`getById`/批量插入等项目统一封装方法。
- **自定义 SQL**：仅在 MP 无法覆盖时使用；XML 归档于 `resources/mapper/`，命名空间与 Mapper 接口全限定名一致。

**依据**：`bak/_sdd/spec/04_后端代码规范/持久层操作API.md`。

## 数据传输

### 命名

- **请求体 / 复杂入参**：`**DTO` 结尾（如 `UserSaveDTO`）。
- **出参 VO**：响应专用对象以 **`VO` 结尾**（历史规范）。
- **实体**：与表对应，命名贴近表语义；**不推荐**无脑加 `Entity` 后缀（历史示例：`OrderInfo` 对应 `ORDER_INFO`）。

### Entity（MyBatis-Plus）

- `@TableName` 必选；主键 **`@TableId(value = "...", type = ...)`**；各列建议显式 **`@TableField("DB_COLUMN")`**（含大小写），避免隐式驼峰误判。
- 使用 **Lombok**（如 `@Data`）减少样板代码；必要时实现 **`Serializable`**。

### DTO / VO 与时间字段

- 日期与时间格式与前端对齐；历史规范要求在 DTO 上对 `Date` 等字段同时使用 **`@JsonFormat`**（Jackson）与工程内约定的 **FastJSON2 `@JSONField`**（若运行时仍双线序列化）。
- **`timezone`** 等与全局配置保持一致（历史中常用 `GMT+8`）。

### 转换

- Entity ↔ DTO/VO：**优先公用转换工具（如历史中 `DtoEntityUtil`）**；避免在 Controller 内手写大批量 `set`。工具类明细见「公共工具」章占位表。

**依据**：`bak/_sdd/spec/04_后端代码规范/数据结构规范.md`。

## 异常处理

| 类型 | 用途简述 |
|------|----------|
| **BusinessException** | 业务规则失败；可带错误编码，错误文案可与模板引擎/缓存配置配合（历史中描述与 Redis 模板相关） |
| **AppException** | 可直接暴露给用户的应用级异常（参数错、三方调用失败说明等） |

由 **全局 `@ControllerAdvice`（或框架等价扩展）** 统一转换为 **`ResponseMessage.error(...)`**，避免各层重复拼装。

**依据**：`bak/_sdd/spec/04_后端代码规范/异常处理规范.md`。

## 日志记录

- 使用 **SLF4J** 门面：`private static final Logger log` 或 Lombok **`@Slf4j`**。
- **禁止**在无脱敏评审前输出完整身份证号、令牌、密钥；`detailMessage` 类字段仅用于排障并按环境开关控制。
- 配置侧：`logback-spring.xml` / `logging.level.*` **以工程为准**。

**依据**：分层与历史项目结构中对 Logback 的约定；Boot 3 沿用常见栈。

## 注释规范

- **公开 API**（Controller 方法、Service 意图、Mapper 中非自解释 SQL）：使用简短中文或中英混合 **Javadoc**，说明用途、前置条件、重要副作用。
- 复杂分支处用 **行注释**解释「为何」而非「做了什么」。
- 避免无意义注释与过期注释（与代码同步维护）。

## 持久层操作

- **首选 MyBatis-Plus**：`LambdaQueryWrapper`、批量 `saveBatch`/`updateBatchById`（若框架启用）、分页 `PaginationInnerInterceptor` 等须在配置类启用。
- **乐观锁 / 多租户 / 字段自动填充**：若 Starter 提供 `MetaObjectHandler`、租户插件等，按官方与团队封装统一启用，勿在业务中重复实现。
- **SQL**：须防注入（`#{ }`）；动态 SQL 可读性优先于过度拼接。
- **`BaseDAO`** 所提供的 `list`、`getById`、`page`、`insertBatch` 等：**根据 `bak/_sdd/spec/04_后端代码规范/持久层操作API.md`**；最终以依赖库实际 API 为准。

---

## 分页操作

- 使用 **MyBatis-Plus `Page`** 与分页插件构造 **`IPage<T>`** 或在项目统一包装类型（历史中 Controller 曾有 `PageInfo` + `ResponseMessage.ok(null, pageInfo)` 写法；落地后应保持 **全队统一的一种分页载体**，避免混用）。
- Controller 分页接口：分页结果放在 **`ResponseMessage.data`**，**不要将分页字段打散进 JSON 外层与 `data` 重复**。
- Query 参数：`page`/`size` 或统一 `pageNum`/`pageSize` **项目内只有一种命名**，建议在接口层与前端对齐。

**依据**：用户澄清（MyBatis-Plus）；历史片段见 `bak/_sdd/spec/04_后端代码规范/分页操作规范.md`、`Controller层规范.md`。

## 统一响应与核心对象

### ResponseMessage（规划）

历史中定义字段包括：`status`（`"0"` 成功、`"1"` 失败）、`code`、`message`、`detailMessage`、`data`、`extra`；构建方式含 **`ok()` / `error()` 静态方法**与 **Builder**。示例类路径曾描述为：`com.insigma.framework.core.ResponseMessage`。

- **Boot 3 落地后**：以实际 Starter 中标量类型与 **`JsonInclude`** 序列化策略为准。
- **失败**：`message` 面向用户，`code` 建议枚举集中管理，`detailMessage` 控制生产可见性。
- Controller **不声明** `ResponseMessage<T>` **泛型方法签名**。

**依据**：`bak/_sdd/spec/04_后端代码规范/ResponseMessage.md`。
