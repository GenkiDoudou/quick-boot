# 数据库设计规范（总册）

> **说明**：本文为单文件总册，章节顺序对齐常见「关系型数据库设计规范」骨架。**主用引擎依据**：仓库内 **`bak/_sdd/database/schema-design.sql`** 及同目录 **`ddls/*.sql`** 中的 DDL（`VARCHAR2`、`NUMBER`、`SEQUENCE`、`COMMENT ON` 等，判定为 **Oracle** 方言）。与 **`sdd/后端代码规范.md`** 中的 **MyBatis-Plus** 持久层选型一致。**当前仓库尚未迁入可编译后端与数据源配置**，JDBC URL、具体 Oracle 版本、字符集、是否 RAC/读写分离等以运维与环境落地为准；首批业务迁移脚本入库后宜对照修订本章。

---

## 概述与使用说明

- **适用范围**：计划与本仓库 **Spring Boot 3.x + MyBatis-Plus** 后端配套的关系型库设计与评审；新建表、改表、索引与评审清单以本章为准。
- **与迁移/ORM**：ORM 侧字段映射、命名与 `@TableField` 等须与本规范一致；若 Java 驼峰与库侧命名不一致，须在实体上显式注明列名（参见后端规范「数据结构」）。
- **代码生成与评审**：脚手架或 AI 生成 DDL 须满足 **命名、类型、主键、索引、注释** 小节；涉及分区、敏感字段须额外走架构/安全评审。
- **可追溯性**
  - 引擎与 DDL 风格：**根据** `bak/_sdd/database/` 下现有脚本归纳。
  - 历史条文对齐：可与 `bak/_sdd/spec/02_数据库设计规范/Oracle数据库设计规范.md` 对照；**本文优先反映仓库内实际 DDL 中出现的做法**（例如 Quartz 表存在 **数据库级外键**，与纯业务表习惯可能不同）。

## 适用数据库与运行环境

| 项目 | 结论或状态 |
|------|------------|
| 关系型引擎 | **Oracle**（自 DDL 推断，见上文依据） |
| 版本 | **待运维确认**（建议文档化最低支持版本，如 12c+ 以便使用 IDENTITY 等特性） |
| 字符集 /  national character set | **待环境确认**（新建库时常用 AL32UTF8；须与 JDBC `NLS`/`oracle.jdbc` 参数一致） |

## 命名规范

- **库 / Schema**：按环境与公司惯例；业务对象建议在固定 Schema 下管理，**待立项命名**。
- **表名**：与现有脚本一致时多为 **大写**、下划线分隔（如 `AA01`、`SYSROLE`、`EMPLOYEE_BASE_INFO`）。**新建表**建议在团队内统一为 **UPPER_SNAKE_CASE**（Oracle 未加双引号时默认大写存储语义）。
- **字段名**：**UPPER_SNAKE_CASE**（与历史 DDL、MyBatis-Plus `@TableField("XXX")` 显式映射一致）。
- **主键约束**：`PK_{表名}` 或与历史一致的主键名。
- **索引**：历史中出现 **`IDX_{表名}_{字段}`**、唯一索引等；新建索引遵循 **`IDX_` / `UNIQ_` + 表缩写 + 字段** 规则，避免过长。
- **序列（SEQUENCE）**：历史中存在 **`SQ_*`、`SEQ_*`** 等多种前缀；新建序列须在团队内统一前缀与缓存策略（`CACHE` / `NOCACHE`），并与主键生成策略文档同步。
- **外键约束**：若启用数据库级外键，命名建议 **`FK_{子表}_{字段}`**，与 Quartz 等第三方脚本风格可区分。

## 数据类型选择（Oracle 为主）

- **整数 / 主键 surrogate**：**NUMBER**；精度尺度按需要设定（如 `NUMBER(12)`、`NUMBER(19)`）。若新项目统一采用 **IDENTITY**（12c+），须在团队内一次性约定并与 MP `@TableId(type = IdType.*)` 对齐。
- **字符串**：短文本 **VARCHAR2(n)**，`n` 按字节或字符语义需在团队明确（Oracle 版本相关）；固定长度可用 **CHAR(n)**；大文本 **CLOB**。
- **日期时间**：历史 DDL 大量 **`DATE`**（含 `DEFAULT SYSDATE`）；新剧表若需毫秒与时区，优先考虑 **TIMESTAMP** / **`TIMESTAMP WITH TIME ZONE`**，并与后端 `jdbcType`/驱动类型映射对齐。
- **布尔 / 标志位**：常见 **`VARCHAR2(1)`**（如 `'0'`/`'1'`）或 **NUMBER(1)**；团队择一并写入枚举映射规范。
- **金额**：**NUMBER(p, s)**（如 `NUMBER(18,2)`），避免浮点。
- **JSON**：若使用 **12c+ JSON** 类型或 **CLOB** 存 JSON，须约定校验与索引策略（JSON Search Index 等）；否则可用独立子表规范化存储。
- **大二进制**：**BLOB**；是否与文件中心表剥离存储须在架构层约定。

**仓库内未见样例的业务表若全部采用新类型策略**：首批迁移落地后应回本节修订。

## 主键与外键

- **主键**：每张业务表须有主键；历史中存在 **单列主键**（含业务键与 surrogate）及 **Quartz 联合主键**；新业务表默认 **单列 surrogate + SEQUENCE 或 IDENTITY**，除非领域明确要求复合主键。
- **序列**：与 **`SEQUENCE`** 配合时须在应用或触发器层统一取号方式，避免并发与缓存语义不一致。
- **数据库外键**：
  - **第三方框架表**（如 **`QRTZ_*`**）：DDL 中含 **`REFERENCES`**，应保持与上游脚本一致。
  - **自有业务表**：历史规范倾向 **应用层维护引用完整性**；是否启用 **FOREIGN KEY** 由团队权衡（迁移成本、级联、在线 DDL）。若启用须写明 **更新/删除规则**（`ON DELETE`/`UPDATE`）。

---

## 索引策略

- **主键 / 唯一**：由约束自动支撑；业务唯一性（证件号、编码等）须 **UNIQUE INDEX**，命名清晰。
- **查询导向**：**WHERE / JOIN / ORDER BY** 高频列建索引；联合索引注意 **列顺序与选择性**。
- **写作平衡**：避免冗余索引；大批量导入场景可评估 **批量加载前临时禁用部分索引**（运维流程单独立项）。
- **函数索引 / 分区索引**：仅在确有性能依据时引入，并补充监控与文档。

---

## 字段约束

- **NOT NULL**：业务必填须声明；可空字段须有默认值或明确 NULL 语义。
- **DEFAULT**：如 **`DEFAULT SYSDATE`**；与 MP 插入策略协调，避免「库默认 vs 应用写入」双轨。
- **CHECK**：用于明显离散取值时约束（与字典表二选一）。
- **枚举 vs 字典表**：固定少量取值可用 **CHECK + VARCHAR2**；可扩展、可维护列表优先 **字典表 + 外键或应用层校验**。

## 迁移与版本管理

- **现状**：仓库根目录 **未发现** Flyway / Liquibase / Prisma 等标准迁移目录；历史 DDL 以 **`bak/_sdd/database/schema-design.sql`** 与 **`bak/_sdd/database/ddls/`** 单表文件形式存在。
- **建议（待后端迁入后选定其一并写入工程 README）**：
  - **Flyway** 或 **Liquibase**：版本化脚本、`V{version}__{description}.sql` 或等价命名；**区分 Oracle 专用脚本目录**（若未来多引擎再分子目录）。
  - **回滚**：生产环境慎用自动 DROP；以 **向前兼容迁移 + 数据修复脚本** 为主。
- **在工具未定前**：变更须有 **评审过的 SQL 文件** 与 **执行记录**（环境、执行人、版本）。

## 安全与敏感数据

- **仓库内无** 加密列、脱敏中间件或审计实现的活性代码证据。
- **原则（待定 / N/A 落地后补）**：连接串与口令不进仓；最小权限账号；敏感列（证件、手机号）考虑 **脱敏视图**、**透明加密** 或 **应用层加密**；重要表保留 **操作人 / 操作时间** 或与 **`SYSOPERATELOG` 类表** 联动策略。
- **审计字段**：历史表中出现 **`CREATE_TIME`/`MODIFY_TIME`/`UPDATE_TIME`**、`UPDATER` 等模式；新剧表建议统一一套命名（见下节）。

## 其他最佳实践

- **时间与操作者**：建议新业务表统一 **`CREATE_TIME`（必填）**、**`UPDATE_TIME`（可空或 ON UPDATE 语义由应用维护）**；必要时 **`CREATOR`/`UPDATER`**；与现有 `DATE` / 未来 `TIMESTAMP` 选型一致即可。
- **软删除**：历史规范倾向 **避免默认软删**；若使用 **`IS_DELETED`/`DEL_FLAG`** 等，须在 MP **逻辑删除** 与全局查询策略上一致。
- **注释**：使用 **`COMMENT ON TABLE` / `COMMENT ON COLUMN`**，与历史脚本一致；注释说明枚举取值含义（如 `::` 分隔的描述风格可与历史对齐）。
- **单表列数**：建议 **≤ 50**；超宽表考虑垂直拆分或 JSON/CLOB 策略评审。
- **大表与分区**：预期 **百万级以上** 访问模式的表，在概要设计阶段评估 **分区表**、历史归档。
- **Quartz / 监控类表**：尽量 **保持与上游开源 DDL 一致**，单独目录管理版本，避免手工随意改列类型。
