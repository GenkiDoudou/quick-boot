三种分层方案对比

目标：为拆微服务做准备 · Maven↔Modulith 一对一 · 薄共享 · 跨域显式 API · 第一阶段暂不拆 system

A

推荐：platform + module-system + app

共享极薄；system 内分 api / internal；app 只负责启动与组装。新业务域按同样模板加 module-xxx。

Maven / Modulith
quickboot-platform　　　← 无业务（异常/安全基建/工具）
quickboot-module-system ← Modulith: system
├ api/　　　← 对外接口 + DTO/事件契约
└ internal/ ← entity/mapper/service/controller
quickboot-app　　　　　← @SpringBootApplication + 模块校验
B

双 jar 契约：system-api + system

每个域拆出独立 *-api Maven 模块，其他域只依赖 api jar。拆微服务时契约可单独发布，但模块数翻倍。

Maven
quickboot-platform
quickboot-module-system-api　← 仅接口/DTO
quickboot-module-system　　　← 实现（Modulith）
quickboot-app
C

现状渐进：收编 common/core，少改名

把 common+core 收敛为 thin platform（可暂保留目录名），system 加 api 包边界，web 改造成 app。迁移成本最低，命名与「一对一」叙事略糊。

演进路径
common + core → platform（薄化）
system　　　→ 增加 api 包 + Modulith 元数据
web　　　　→ app（启动 + 校验）

A 适合你如果…

  • 想清晰模板，后面加域照抄
  • 暂不拆 system，但边界规则要先立住
  • 接受一次命名整理

需注意

  • B：契约强，但 Maven 模块膨胀快
  • C：最快落地，长期一对一叙事弱一些
  • 三者都应：禁止跨域依赖 internal
