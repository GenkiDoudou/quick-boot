设计 §2：模块内部结构与依赖规则

方案 A · 以 module-system 为模板；新域照抄

推荐包结构（module-system）

io.github.genkidoudou.system
api/　← Modulith 允许被其他模块依赖
XxxFacade / XxxQueryService（接口）
dto / command / event（契约类型）
internal/　← 默认封闭，仅本模块可见
controller · service · mapper · entity · config
api 接口的实现类放这里
package-info.java　← @ApplicationModule / 开放包声明
允许
  • app → 所有 module + platform
  • module-X → platform
  • module-X → module-Y.api
  • 同模块 internal 随意协作
禁止
  • module-X → module-Y.internal
  • platform → 任何业务 module
  • module 之间循环依赖
  • 把业务实体/Mapper 放进 platform

跨模块调用约定（你选的显式 API）

他域需要本域能力时：只注入 api 中的接口；DTO/事件定义也只放 api。实现与表结构留在 internal。第一阶段 system 暂无他域，先把现有对外扩展点抽到 api（如字典查询、用户查询），避免以后再挖。

Controller 放哪？

放在各业务模块的 internal（与现网 system 一致）。app 不写业务接口，只做装配与横切（Sa-Token、全局异常若已在 platform 则保持）。
