设计 §3：现状迁移与验证

从 common/core/system/web 演进到 platform + module-system + app

映射关系

演进映射（逻辑）
quickboot-common + quickboot-core　→　quickboot-platform（薄化：去掉/上移业务相关）
quickboot-system　　　　　　　　　→　quickboot-module-system（加 api/internal）
quickboot-web　　　　　　　　　　→　quickboot-app

命名可一次改干净，或分两步（先结构后改 artifactId）。推荐一次改名，避免长期双名。

迁移顺序（建议）

  1. 引入 Spring Modulith 依赖与 ApplicationModules 测试骨架（先在现结构验证也能跑）
  2. 合并/薄化 common+core → platform；切断对 system 的反向依赖
  3. system 包整理为 api + internal；声明 @ApplicationModule
  4. web → app；scan/MapperScan 指向新包；CI 加上 Modulith 结构测试
  5. 文档化「新域模板」：复制 module-system 骨架即可

成功标准（可验证）

  • ApplicationModules.of(...).verify() 通过（无非法跨模块依赖）
  • Maven 依赖图：platform 不依赖任何 module-*；module 互不依赖对方 internal
  • 现有登录/用户/字典等主路径回归可用
  • 新增业务域有书面模板（模块名、包名、api 约定）

刻意不做（YAGNI）

  • 第一阶段不拆 system 为多域
  • 不单独建 *-api Maven 模块
  • 不强制上事件驱动（保留显式 API；事件可后加）
  • 不在本设计里改前端或库表
