# 安全防火墙：接口幂等（firewall/idempotent）原始需求

## 背景
- 用户重复点击、网络重试、网关重放等会导致接口重复执行（重复下单/重复扣款等）。
- 需要通用的幂等控制能力：在约定时间窗口内对「同一幂等 token」的重复请求予以拒绝；业务侧仍须保证自身语义幂等（如业务单号去重）。

## 已定案约束（产品口径）
1. **默认关闭**：`qc.security.firewall.idempotent.enabled` **默认 `false`**，需显式开启后生效。
2. **仅 TOKEN 策略**：幂等键**只**由配置的请求头（默认 `X-Idempotent-Token`）取值参与构造（配合全局/注解 `keyPrefix` 等）；**不**使用方法签名、URL、参数 hash、`URL_USER`、自定义 `IdempotentKeyGenerator` 等策略。
3. **不校验用户标识参与键**：不因 `X-User-Id`/session/IP 等拼装键；与第 2 条一致，键材料仅为 token 字符串（及前缀分段）。
4. **存储双实现与自动回落**：同时支持 **Redis** 与 **Caffeine**。**默认自动选择**：当项目中存在可用 Redis 客户端/`RedisConnectionFactory` 等约定 Bean 时优先用 Redis；**若未使用 Redis 或未注入可用 Redis Bean**，则使用 **Caffeine**（单机内存）。允许配置项强制指定其一（与实现阶段商定具体键名，如 `cache-type: redis|caffeine|auto`）。
5. **重复请求的 HTTP 语义**：重复命中时 **HTTP 状态码仍为 200**，通过统一响应 **`R.code` 等业务码** 返回 **`30201`**（及文案），**不**依赖 409/429 等 HTTP 层语义区分。
6. **不强制校验 token 是否存在**：请求**未携带**幂等 token 时，**不做幂等占位、不拦截**，业务按普通请求执行；**不**因缺 token 返回单独错误码或错误提示。

## 目标
- 提供 `@Idempotent` 注解用于方法级幂等（参数侧重 TTL、`prefix`、`deleteAfterExecution` 等，**不设策略枚举切换**）。
- 支持「自动拦截指定请求方法」模式（配置 `interceptMethods[]`），与注解模式**共享同一套 TOKEN 键规则**。
- 支持 Redis / Caffeine 存储，**自动回落**规则见上文。
- **不在本需求范围**：多策略枚举、自定义 `IdempotentKeyGenerator`、基于参数 hash 的键。

## 功能需求
### 1. 启用与拦截范围
- 启用条件：`qc.security.firewall.idempotent.enabled=true`（**默认 `false`**）。
- 两种工作方式：
  1) 显式注解：仅拦截标注 `@Idempotent` 的方法（且满足 token 规则时参与幂等）。
  2) 自动拦截：配置 `interceptMethods[]`（如 POST/PUT/DELETE）后，对满足条件的请求在 **携带 token** 时做幂等。
- 支持 `excludeUrls[]`（Ant）：命中后不做幂等校验。

### 2. 幂等键生成（仅 TOKEN）
- 从请求头读取幂等 token，头名由配置 `tokenHeader` 指定（默认 `X-Idempotent-Token`）。
- **仅当**头存在且取值经修剪后**非空**时，才构造存储键并执行 `setIfAbsent`；**头缺失或为空则不进入幂等逻辑**（见已定案第 6 条）。
- key 前缀：全局 `keyPrefix`；注解 `prefix()` 可补充分段。
- **不对** token 格式、预注册、颁发方做服务端校验；任意非空字符串均可作为幂等维度（客户端保证同一业务操作用同一 token）。

### 3. 存储与过期
- 存储接口：
  - `setIfAbsent(key, value, expireTime, timeUnit)`：原子占位
  - `delete(key)`：删除占位
- 过期时间来源：
  - 注解 `expireTime/timeUnit` 优先
  - 否则使用全局 `expireTime/timeUnit`
- Redis / Caffeine 选择与回落见已定案第 4 条。
- 异常处理：
  - 已存在（重复请求）：抛出 `IdempotentException`（或等价机制），经统一异常处理转为 **`HTTP 200` + `R.code=30201`**
  - 目标方法抛异常时应删除 key，允许重试
  - `deleteAfterExecution=true` 时执行完成后删除 key（允许再次执行）

## 配置项
- 前缀：`qc.security.firewall.idempotent`
  - `enabled`（默认 `false`）
  - `interceptMethods[]`
  - `excludeUrls[]`
  - `expireTime/timeUnit`
  - `keyPrefix`
  - `defaultMessage`（如用于 30201 文案）
  - `tokenHeader`（默认 `X-Idempotent-Token`）
  - `cacheType`（建议支持 `auto|redis|caffeine`：`auto` 为「有 Redis Bean 用 Redis，否则 Caffeine」）

## 依赖与边界
- 依赖：Spring AOP；Redis 或 Caffeine 实现原子 `setIfAbsent` + TTL。
- 边界：
  - 须满足并发下「占位」原子性；Caffeine 多节点互不共享，**仅适合单机或无Redis时的退化**。
  - 业务侧仍需确保接口本身具备幂等语义（例如以业务单号去重）。

## 验收标准
- **开启**且请求**携带相同非空 token**、在幂等窗口内重复调用：响应 **HTTP 200**，`R.code`（或项目约定业务码字段）为 **`30201`**。
- **首次**请求成功执行；业务方法异常时 key 被清理，允许使用**同一 token**重试（仍为首次语义）。
- **未携带**或 token **为空**：不参与幂等，**不**返回缺 token 类错误，业务正常执行。
- Redis 不可用时自动使用 Caffeine 的部署场景下，单测或文档说明多实例局限。
