## Context

当前系统已具备参数设置基础 CRUD 能力，但“参数治理”层面的关键约束在实现与文档之间存在不一致风险：`configKey` 唯一性边界、内置参数删除保护、敏感值脱敏展示、缓存刷新粒度、导出范围与中文化提示等。该变更需要同时约束后端规则与前端交互，属于跨模块（`quickboot-web` + `quick-ui`）的一致性治理改造。

约束条件：
- 复用现有 `/system/config` 接口体系，不新增接口形态。
- 不引入新的参数值类型模型，保持字符串值。
- 不新增独立参数历史表，沿用操作日志审计能力。

## Goals / Non-Goals

**Goals:**
- 固化参数设置的业务规则为可验证规范，避免前后端实现偏差。
- 确保内置参数与敏感参数具备最小必要保护策略。
- 明确缓存刷新与导出的操作边界，降低误操作与性能风险。
- 统一页面与错误提示文案为中文，提升运维可用性。

**Non-Goals:**
- 不做参数分层（平台级/业务级）与租户化改造。
- 不新增“按键刷新缓存”能力。
- 不新增独立配置变更历史库表。
- 不扩展新的参数值类型校验体系（JSON/数字/布尔）。

## Decisions

### 决策 1：`configKey` 唯一性以后端为最终裁决
- 方案：在后端 Service/持久层执行唯一性校验并返回明确中文错误；前端仅做体验性提示。
- 理由：避免并发场景下前端预校验失效，确保数据一致性。
- 备选：
  - 前后端双强校验：实现更复杂且最终仍以后端为准。
  - 仅前端校验：无法保证并发一致性，不采用。

### 决策 2：系统内置参数采用“可改不可删”策略
- 方案：保留查询、导出、值编辑能力，删除操作在后端强制拦截。
- 理由：兼顾可运维与安全保护，避免误删关键配置导致系统不可用。
- 备选：
  - 内置参数完全只读：运维灵活性不足。
  - 内置参数可删除：风险不可接受。

### 决策 3：敏感参数默认脱敏，明文能力受权限控制
- 方案：前端列表与详情默认脱敏展示；明文查看/编辑由单独权限点或受控动作触发；后端按键名策略返回脱敏值。
- 理由：降低敏感信息暴露面，满足最小权限原则。
- 备选：
  - 全量明文展示：安全风险高。
  - 完全不支持明文：故障排查成本高。

### 决策 4：缓存刷新仅支持全量刷新
- 方案：保留 `/system/config/refreshCache` 全量刷新入口，不扩展按键刷新。
- 理由：实现简单、行为确定，避免部分刷新导致的状态不一致理解成本。
- 备选：
  - 增加按键刷新：需要新增接口、权限与一致性语义，当前不做。

### 决策 5：导出按筛选条件全量结果
- 方案：导出行为基于查询条件而非当前分页。
- 理由：符合运维审计与配置核查的典型使用场景。
- 备选：
  - 仅导出当前页：不符合后台管理导出预期。

## Risks / Trade-offs

- [Risk] 脱敏规则依赖“敏感键识别策略”，误判会导致过度脱敏或漏脱敏  
  → Mitigation：定义可配置敏感键模式（如 `password|secret|token|key`）并补充回归用例。

- [Risk] 后端唯一性校验若仅在应用层，仍可能受并发写入影响  
  → Mitigation：数据库层补唯一索引或唯一约束兜底，并做异常映射为中文业务提示。

- [Risk] 全量缓存刷新在高频运维场景下可能造成短时抖动  
  → Mitigation：限制触发权限、增加操作确认与成功/失败反馈，必要时评估异步刷新。

- [Risk] 文案统一中文改造可能遗漏边角提示  
  → Mitigation：梳理页面按钮、弹窗、异常提示清单并逐项验收。

## Migration Plan

1. 对齐后端参数规则：唯一性、内置参数删除保护、脱敏返回策略、中文错误文案。  
2. 对齐前端页面行为：脱敏展示、中文文案、导出与刷新交互确认。  
3. 执行联调验证：新增/编辑/删除/导出/刷新缓存/敏感值显示与权限校验。  
4. 灰度发布并观察操作日志与异常告警。  
5. 回滚策略：若出现治理规则不兼容，先回滚前端展示策略，再回滚后端规则开关或版本。
