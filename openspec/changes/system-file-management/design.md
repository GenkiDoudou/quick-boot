## Context

仓库当前已具备 `quickboot-common` 的通用文件存储能力（`FileTemplate` + 本地/MinIO 后端 + 分类与路径校验 + `FileUploadHook`），但该模块按既有边界 **不提供对外 HTTP Controller**，也没有统一的文件元数据登记与管理端页面。

本变更在不破坏现有模块边界的前提下，引入：

- 面向管理端的「系统文件管理」能力（API + 页面 + 权限菜单）
- 全系统上传文件的自动登记（通过 `FileUploadHook` 在上传成功后写入元数据表）

约束与已确认决策（来自用户澄清）：

- 方案：**FileTemplate 上传 Hook 自动登记 + 文件管理页提供上传/列表/预览/下载/删除**
- 删除语义：**逻辑删 + 同步删除存储对象**
- 预览交互：**图片/视频弹窗预览，其他文件新窗口打开**
- 列表字段（最小集）：文件名、大小、扩展名、上传时间、上传人

## Goals / Non-Goals

**Goals:**

- 新增 `system-file-management` 领域能力：提供文件元数据持久化、查询与管理 API，并在 `quick-ui` 提供对应页面。
- 通过 `FileUploadHook` 实现“全系统上传自动登记”：
  - 任意业务使用 `FileTemplate.upload(...)` 成功后，都能在 `sys_file` 产生登记记录。
  - 登记失败时，上传必须失败且不得遗留不可管理的“孤儿对象”（具体通过回滚/删除保证）。
- 对外能力满足：上传、分页列表、预览（URL）、下载（附件）、批量删除。

**Non-Goals:**

- 不做业务关联（业务单号/来源模块）、不做复杂文件转换预览（Office 转 PDF 等）。
- 不做分片/断点续传、版本管理、回收站与延迟清理。
- 不要求改造现有业务上传调用方式（通过 Hook 覆盖）。

## Decisions

### 决策 1：以 `FileUploadHook.afterUpload` 做全局登记（而非仅在文件管理 Controller 登记）

- **选择**：在 `quickboot-common` 的 `FileTemplate` 上传成功后触发登记 Hook，写入 `sys_file`。
- **理由**：满足“存储所有上传文件”的需求；避免要求业务模块逐一改造；登记逻辑集中、可控。
- **备选方案**：
  - 仅文件管理页面上传才登记：无法覆盖业务侧上传，违背核心目标。
  - 扫描本地目录/MinIO bucket：无法可靠获得原始文件名、上传人、时间等审计信息，且安全与性能风险较大。

### 决策 2：管理端操作以 `fileId` 为主键（不直接用 `relativePath`）

- **选择**：列表与操作（预览/下载/删除）均以 `fileId` 作为前端参数；后端通过 `fileId` 查 `relativePath` 并调用 `FileTemplate`。
- **理由**：避免前端传递路径字符串带来的安全问题与耦合；便于扩展权限与审计。
- **备选方案**：直接以 `relativePath` 下载/预览：容易被滥用或暴露存储结构，且不利于审计与扩展。

### 决策 3：删除采用“逻辑删 + 同步删除存储对象”

- **选择**：删除时记录 `deleted/deleteBy/deleteTime`，并同步调用存储删除对象。
- **理由**：保留审计与可追踪，同时控制存储空间增长；与“文件管理”语义一致。
- **备选方案**：仅逻辑删对象保留（占空间，后续仍需清理机制）；仅物理删（无法审计，不推荐）。

### 决策 4：预览接口返回可访问 URL（由前端决定弹窗或新窗口）

- **选择**：后端 `GET /system/file/view/{fileId}` 返回 `url`（由 `FileTemplate.view(relativePath)` 或等价能力生成）；前端按文件类型决定弹窗预览或 `window.open`。
- **理由**：保持 `common-file-storage` 的模块边界；前端交互可统一且简单；对本地/MinIO 兼容。
- **备选方案**：后端直接流式输出预览：实现更复杂，且与下载语义容易混淆。

## Risks / Trade-offs

- **[Hook 登记失败导致上传失败]** → **缓解**：明确业务约束并在 `common-file-storage` 规范中补齐；实现中确保异常路径会清理已写入对象，避免“失败但对象存在”。
- **[无登录态上传时无法记录上传人]** → **缓解**：在规范中明确无登录态的写入策略（如 userId=0、userName=系统/匿名），并确保仍可登记。
- **[文件类型识别不一致影响预览]** → **缓解**：前端以扩展名与 `contentType` 结合判断，默认回退为新窗口打开。
