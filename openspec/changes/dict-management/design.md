## Context

当前仓库尚无完整的系统字典能力，业务状态与展示文案主要分散在前后端硬编码中，难以统一治理。已有基础设施（统一响应 `R`、Validation、自定义异常、全局异常处理、缓存能力、`@/packages` 组件）可直接复用，因此本次设计聚焦在“补齐主从字典域模型与操作闭环”，而非新增基础框架。

已确认约束：
- 字典管理与字典项管理采用主从双页。
- 字典项必须强绑定 `dictType`。
- 写接口统一使用 `POST` 语义，不使用 `PUT/DELETE`。
- 提供单类型与全量缓存刷新。
- 前端优先使用 `@/packages` 组件。

## Goals / Non-Goals

**Goals:**
- 建立字典类型（主）与字典项（从）的完整 CRUD、查看、导出与缓存刷新能力。
- 统一接口契约与参数校验策略，确保前后端行为一致。
- 建立“删除字典前校验存在字典项”的安全约束，避免脏数据。
- 在前端形成稳定的主从路由与交互模式。

**Non-Goals:**
- 不引入字典版本化、发布审批、多租户隔离等高级治理能力。
- 不修改 `R`、traceId、国际化等基础公共契约。
- 不额外引入新的表格或缓存中间件依赖。

## Decisions

### 决策 1：采用主从双页而非单页弹窗
- 选择：`/system/dict/type` + `/system/dict/data/:dictType`。
- 原因：职责边界清晰，字典项可独立筛选与导出，后续扩展成本低。
- 备选：单页 Tab 或弹窗嵌套管理。
- 放弃原因：状态耦合重，复杂交互与权限控制难维护。

### 决策 2：写接口统一 `POST` 动作语义
- 选择：新增 `POST /...`，修改 `POST /update`，删除 `POST /remove/{id}`。
- 原因：与仓库已确认规范一致，减少跨模块接口风格分裂。
- 备选：REST `PUT/DELETE`。
- 放弃原因：与当前团队接口规范冲突，增加接入与审查成本。

### 决策 3：删除字典前做从表存在性校验
- 选择：有字典项则拒绝删除并返回业务失败。
- 原因：避免孤儿数据或级联误删带来的配置事故。
- 备选：级联删除。
- 放弃原因：高风险且不可逆，缺少业务确认链路。

### 决策 4：缓存刷新同时支持“单类型 + 全量”
- 选择：提供两个刷新入口。
- 原因：兼顾精准更新与批量维护场景。
- 备选：仅全量或仅单类型刷新。
- 放弃原因：单一模式无法覆盖运维与业务两类诉求。

### 决策 5：前端优先 `@/packages` 组件
- 选择：按钮、弹窗、表格、字典标签优先采用 C7 组件。
- 原因：交互一致性更高，减少重复样板。
- 备选：全部原生 Element Plus。
- 放弃原因：会弱化仓库既有组件体系，增加页面风格分裂。

## Risks / Trade-offs

- [风险] 历史数据出现 `dictType` 重复或 `dictValue` 冲突。
  - Mitigation：迁移前执行数据巡检并建立唯一约束。

- [风险] 缓存刷新后短时读写不一致。
  - Mitigation：统一刷新流程并记录操作日志，必要时串行化刷新动作。

- [风险] 旧调用方仍使用 `PUT/DELETE`。
  - Mitigation：在变更说明中明确 BREAKING，前端 API 层统一收口。

## Migration Plan

1. 新增字典类型与字典项表，落地唯一约束、状态与审计字段。
2. 实现后端主从接口、业务校验、异常映射与缓存刷新。
3. 新增前端主从页面与路由，替换为统一 API 调用。
4. 联调后执行导出与刷新场景验证。
5. 发布时同步变更说明，强调写接口语义调整。

回滚策略：
- 若发布异常，可先下线新路由与入口；数据库层保留新增表不影响既有能力。
- 若接口不兼容，可临时在网关/API 层做兼容转发（限过渡期）。

## Open Questions

- 缓存键命名是否已有统一前缀规范，实施前需与现有缓存模块核对。
