## Context

当前仓库包含 Spring Boot 3 后端与 Vue 3 前端，尚未形成完整的参数设置模块闭环。业务已明确需要参数查询、维护、导出、缓存刷新与审计能力，并要求与现有系统管理页面风格和权限体系一致。

约束条件包括：`configValue` 按字符串处理、不新增值类型字段、接口修改/删除语义统一为 `POST`、系统内置参数不可删除且仅允许修改 `configValue`。

## Goals / Non-Goals

**Goals:**
- 提供参数设置全流程能力：查询、分页、新增、编辑、删除、导出、全量刷新缓存。
- 在后端落实 `configKey` 全局唯一和系统内置参数保护规则。
- 保持前后端分层与接口风格一致，复用既有操作日志完成审计。
- 采用最小改造路径，降低回归风险并快速落地。

**Non-Goals:**
- 不实现敏感值识别、脱敏展示、明文查看/编辑权限模型。
- 不引入新存储模型（如参数历史表、值类型扩展表）。
- 不做跨模块大规模重构。

## Decisions

### 决策1：采用最小改造方案A
- 选择：围绕现有参数管理链路补齐规则与交互，不扩展新域模型。
- 原因：需求边界清晰，时间优先，且可显著降低联动风险。
- 备选：
  - 策略层抽象（可维护性更高，但首版成本更高）。
  - 模块标准化重构（收益长期化，但超出本次范围）。

### 决策2：接口更新/删除统一为 POST
- 选择：将更新、删除、刷新缓存等写操作统一为 `POST`。
- 原因：符合项目协作约束，避免参数模块接口风格孤岛。
- 备选：保留 `PUT/DELETE`（短期兼容强，但会与仓库约束冲突）。

### 决策3：后端强校验优先，前端提示为辅
- 选择：`configKey` 唯一性、内置参数删除限制、内置参数编辑边界由后端强校验兜底。
- 原因：避免绕过前端导致规则失效，保障数据一致性。
- 备选：仅前端限制（实现快但不安全）。

### 决策4：审计复用操作日志，不新增历史表
- 选择：参数变更审计复用现有日志体系。
- 原因：满足当前审计诉求并减少数据模型变更。
- 备选：新增历史表（审计更细粒度，但超出本次投入上限）。

## Risks / Trade-offs

- [风险] 参数接口路径与既有调用方不一致导致兼容问题 → [缓解] 提前盘点旧接口引用，必要时保留短期兼容入口并标注废弃。
- [风险] 内置参数可编辑边界实现不严导致越权修改 → [缓解] 在 Service 层做字段白名单校验，并补充单元测试覆盖。
- [风险] 全量刷新缓存同步执行耗时波动影响体验 → [缓解] 增加明确加载态与超时错误提示，后端记录耗时日志。
- [风险] 导出按筛选全量查询带来压力 → [缓解] 复用分页查询条件构造，限制单次导出规模并记录审计。

## Migration Plan

1. 后端先完成参数写接口重构与规则校验，保持查询接口可用。
2. 前端接入新接口并完成页面交互对齐，联调导出与刷新缓存。
3. 打通权限点与操作日志，执行模块级回归验证。
4. 发布时先灰度到管理端账号，观察日志与缓存刷新耗时。
5. 回滚策略：保留发布前后端版本回滚包，异常时整体回滚并恢复旧接口映射。
