# 生成前端代码规范（单文件）

## 目标

- 在**当前工作区对应仓库根目录**下，生成 **一份合并后的 Markdown**：`sdd/前端代码规范.md`。
- **禁止**在未探测、未澄清前假定技术栈（不要用「默认 Vue3 + Vite」等替代真实结论）。
- **禁止**依赖仓库外的示例目录或本技能正文未列出的外部文件路径；执行时**只**根据当前项目代码与用户澄清内容写作。
- 若 `sdd` 目录不存在则创建。

## 章节顺序（必须遵守）

顶层 `##` 标题按下列顺序输出（与标准前端规范目录骨架一致；内容可因项目删减，但顺序不变）：

1. **概述与使用说明**（各章对代码生成/协作的约束说明；标明本文档为单文件总册）
2. **技术栈**
3. **工程目录结构**
4. **文件命名规范**
5. **文件存放规范**
6. **接口调用规范**
7. **公共样式规范**
8. **功能路由**（功能与路由关系；无路由时写「待补充」并标明依据）
9. **公共函数调用方法**
10. **字典使用规范**（有则写实现约定；无则写「未使用」或按用户澄清写计划，勿编造）
11. **自定义组件清单**（表格为主；重要组件用 `###` 小节写使用要点：props、场景、注意事项，勿仅占位「组件1/2」）
12. **说明**（维护原则、与项目内其他规范的衔接——可短）

章节内部可用 `###` 细分；不必为每章单独拆文件。

---

## 阶段一：探测是否存在前端项目

在仓库根目录及**合理子路径**中查找前端工程证据，**综合判断**，不要只看根目录 `package.json`。

### 应检查的线索（示例，可扩展）

- `package.json` 中的依赖与脚本：`react`、`vue`、`@angular/core`、`svelte`、`next`、`nuxt`、`vite`、`webpack`、`rollup`、`@rspack/core` 等。
- 特征配置文件：`vite.config.*`、`webpack.config.*`、`angular.json`、`next.config.*`、`nuxt.config.*`、`svelte.config.*`、`astro.config.*` 等。
- 典型源码目录：`src/`、`app/`、`pages/`、`components/` 等与框架匹配的入口（`main.tsx`、`main.ts`、`App.vue`、`app/layout.tsx` 等）。

### 单体仓库 / 多包仓库

- 搜索 `packages/*`、`apps/*`、`clients/*`、`frontend`、`web`、`admin`、`ui` 等常见目录下是否另有 `package.json`。
- 若发现 **多个** 可能的前端根目录：列出候选路径与依据，**请用户指定**要针对哪一个生成规范；**在用户选定前不要生成文档**。

### 判定结果

- **找到且唯一（或用户已选定）**：进入 **阶段二（分析并生成）**。
- **找不到**：进入 **阶段三（仅澄清，等待答复）**。**在此阶段不得创建或写入** `sdd/前端代码规范.md`。
- **仅有测试脚手架、示例子项目**：向用户确认是否以该子路径为规范对象；未确认前不生成。

---

## 阶段二：基于代码分析填写规范

在判定的前端根目录下：

- 从 `package.json`（及 lockfile 如有）整理**技术栈**：框架、语言、构建、UI 库、路由、状态、HTTP、样式方案、Lint/Format 等；**只写项目中真实存在的**，未使用的不编造。
- **工程目录结构**：根据实际目录树总结，并配合文字说明各目录职责；**仅当仓库中确实存在某类目录/框架约定时再写**，不抄模板里的虚构名称。
- **命名与存放**：从现有 `components`、`views`、`api`、`utils` 等归纳规则；若项目不一致，说明「当前差异」并给出建议统一方向。
- **接口调用**：定位 axios/fetch/ofetch、封装文件、拦截器、环境变量中的 API base；摘录关键模式（勿贴密钥）。
- **公共样式**：全局样式入口、CSS 变量、预处理、`scoped` 约定等。
- **功能路由**：从路由配置文件或约定式路由梳理「功能 ↔ 路径」表。
- **公共函数**：从 `utils`、`hooks`、`composables`、`lib` 等归纳入口与用法。
- **字典**：若代码中存在字典/枚举/codeTypes 等实现，写入「字典使用规范」；否则如实写未使用，或用户计划在澄清中已说明则按答复写。
- **自定义组件**：从统一导出、全局注册或 `components` 目录扫描；每个组件以 `### 组件名` 撰写要点，**一律以当前仓库源码为准**。

完成分析后，按上文章节顺序写入 `sdd/前端代码规范.md`。

---

## 阶段三：未检测到前端时 — 只澄清，不生成

在无法可靠定位前端工程时：

1. **立即停止**，不创建、不写入 `sdd/前端代码规范.md`。
2. 向用户发起澄清时，**禁止只抛裸问题**（例如仅问「用什么框架？」）。每个待确认维度必须写成：
   - **要确认什么**（一句话）；
   - **选项列表**：用 **A、B、C、D…** 依次编号（同一维度内连续字母，通常 2～4 项；必要时可到 E、F），每项一行，附简短适用场景或得失；
   - **推荐项**：在**恰好一项**选项旁标注 **（推荐）**，或在该维度末尾单独写一行 **`本项推荐：X`**（X 为字母），二者择一、勿矛盾；**必须让用户一眼看出默认建议**；
   - **请用户**回复字母（可多项组合，如「技术栈选 A，构建选 C」）、或「按全部推荐项」、或说明与选项不同的自定义方案。
   - 若选项优劣接近，**仍须指定唯一推荐字母**，并在推荐项说明中用一句话交代为何优先于次选。
3. 澄清应覆盖的维度与**呈现方式**（每维均须 **A/B/C/D… + 唯一推荐标注**；下列文字仅示意内容方向，勿当成用户已选定）：
   - **框架与语言**：用 A/B/C… 枚举可选栈（如 Vue3+TS、React+TS、其他）；说明对目录与状态的影响；**标注推荐字母**。
   - **构建工具**：Vite、Webpack/Rspack、框架内置等列为选项；**标注推荐**。
   - **UI 与样式**：组件库 + 样式方案组合列为多项；**标注推荐组合**。
   - **路由与状态**：官方 Router、文件式路由、Pinia / Zustand / Redux 等列为选项；**标注推荐**。
   - **HTTP 与接口**：Axios 封装、fetch、其他列为选项；**标注推荐**。
   - **目录与 monorepo**：单仓分层、apps/packages 等列为选项；**标注推荐**。
   - **字典 / 全局枚举**：需要联动、首版不做、后续再上等列为选项；**标注推荐**。
   - **其他约束**（可选）：同样 **A/B/C… + 推荐**。
4. **等待用户完整答复**（或用户明确表示「全部按推荐项」「技术栈 A + 构建 C …」）后，再进入 **阶段四**。用户答复中未覆盖的维度，若此前已给出推荐，可再问一轮「是否采纳推荐 **X**」或沿用用户在总则中的指示，**仍不得在无确认时擅自写入最终规范**。

在用户答复之前，若用户催促输出，应重申：需要先完成 **带 A/B/C/D 选项与推荐标注** 的澄清并得到确认，**收到答复后**才会生成文件。

### 澄清表述示例（结构示意）

```markdown
### 待您确认：技术栈

- **需确认**：本项目计划采用的前端框架与是否使用 TypeScript。
- **选项**：
  - **A**（推荐）：Vue 3 + TypeScript + Composition API — 企业后台常见，类型与组件生态成熟。
  - **B**：React 18 + TypeScript — 组件模式灵活，便于大型团队分工。
  - **C**：Vue 3 + JavaScript — 上手快，类型约束较弱。
  - **D**：其他（请说明框架与是否 TS）。
- **本项推荐：A**
- **请您**：回复字母（如 `A`），或多维一并回复；或说明自定义方案。
```

（示例中可同时使用选项旁的 **（推荐）** 与 **本项推荐：A** 以强化可读性；若仅用其一，须保证全文格式统一、推荐字母唯一。）

---

## 阶段四：按澄清生成基础规范（无现成前端工程时）

仅在 **阶段三已得到用户答复** 后执行：

- 按上文相同章节顺序生成 `sdd/前端代码规范.md`。
- 内容以用户澄清为准；无法从仓库验证的段落须标注「基于用户澄清，待项目落地后核对」之类说明，**不得假装已通过代码分析验证**。

---

## 写作与质量要求

- **单文件**：全文一个 `.md`，内部用标题层级组织；不要用「见仓库中另一份规范文件」代替正文（除非用户明确指定了项目内已有文档路径并可摘录）。
- **可追溯**：从代码分析得出的结论须注明依据（例如「根据 `xxx/package.json`」「根据 `src/router`」）；来自用户澄清的须注明「根据用户说明」。
- **语言**：简体中文为主；代码标识符、包名保持原文。
- **简洁**：避免整份粘贴依赖列表；技术栈用分类列表即可。

---

## 完成后

- 告知用户输出路径：`sdd/前端代码规范.md`。
- 若存在未决项（多前端根目录未选、澄清未完成等），明确列出后续待办。
