# 生成数据库设计规范（单文件）

## 目标

- 在**当前工作区对应仓库根目录**下，生成 **一份合并后的 Markdown**：`sdd/数据库设计规范.md`。
- **禁止**在未探测、未澄清前假定数据库类型（不要用「默认 MySQL」等替代真实结论）。
- **禁止**依赖仓库外的示例目录或本技能正文未列出的外部文件路径；执行时**只**根据当前项目证据与用户澄清内容写作。
- 若 `sdd` 目录不存在则创建。

## 章节顺序（必须遵守）

顶层 `##` 标题按下列顺序输出（与常见「关系型数据库设计规范」总册骨架一致；**方言差异**写在对应章内的 `###` 下，不拆多文件；顺序不变）：

1. **概述与使用说明**（本文档用途、与迁移/ORM 的关系、代码生成或评审时的必读范围）
2. **适用数据库与运行环境**（引擎与版本、字符集/排序规则、时区、是否读写分离/多租户等——**仅写可验证或用户已确认的**）
3. **命名规范**（库、Schema、表、字段、索引、约束、序列等）
4. **数据类型选择**（整数、字符串、时间、布尔、金额、JSON、大对象等；按**主用引擎**展开，其他引擎可简写「若使用 … 则 …」）
5. **主键与外键**（主键策略、是否使用数据库外键约束、联合主键与替代键约定等）
6. **索引策略**（单列/联合、唯一、覆盖、过度索引、方言特有索引类型若适用）
7. **字段约束**（NULL、默认值、CHECK、枚举与字典表策略等）
8. **迁移与版本管理**（Flyway、Liquibase、Prisma Migrate、其他；目录约定、命名、回滚策略；**无则写未使用或按澄清规划**）
9. **安全与敏感数据**（脱敏、加密列、审计字段、权限与连接配置原则；**项目无实践则写待定或 N/A**）
10. **其他最佳实践**（审计时间戳、软删除、注释、单表列数建议、分区与大表等——与项目实际对齐）
11. **说明**（维护责任、与项目内其他文档的衔接——可短）

章节内部可用 `###` 细分；全文必须保持**单文件**。

## 阶段一：探测是否存在数据库相关证据

在仓库根目录及**合理子路径**中查找数据库使用证据，**综合判断**。

### 应检查的线索（示例，可扩展）

- **应用配置**：`application*.yml`、`application*.properties`、`.env*` 中的 JDBC URL、`spring.datasource`、或 `DATABASE_URL`、`django`/`DATABASES`、Prisma `datasource`、`typeorm`/`DataSource` 等。
- **迁移与脚本**：`db/migration`、`flyway`、`liquibase`、`prisma/migrations`、Rails `db/migrate`、`.sql` 初始化脚本等。
- **基础设施**：`docker-compose*`、`kubernetes` 清单中的 MySQL、PostgreSQL、Oracle、MariaDB、SQL Server 等**有状态服务**（镜像名、环境变量）。
- **ORM / 客户端**：`pom.xml`/`build.gradle` 中的数据库驱动坐标；`pg`、`mysql2`、`database` 等包与配置同现时可佐证。

### 单体仓库 / 多模块

- 若 **多套数据源或多套迁移目录** 分属不同子项目：列出候选路径与依据，**请用户指定**以哪一套为准生成规范；**在用户选定前不要生成文档**。

### 判定结果

- **找到明确引擎或连接信息（或用户已选定目标库）**：进入 **阶段二（分析并生成）**。
- **仅有 Redis/Mongo 等非关系型中间件、无任何关系型库证据**：进入 **阶段三（仅澄清，等待答复）**，不得假装已是「完整库设计规范」。
- **找不到可靠证据**：进入 **阶段三**。**在此阶段不得创建或写入** `sdd/数据库设计规范.md`。

---

## 阶段二：基于项目证据填写规范

- **适用数据库与运行环境**：从配置、镜像、驱动推断引擎与版本范围、字符集及时区线索；无法确定处标注「待运维/配置确认」。
- **命名 / 类型 / 主外键 / 索引 / 约束**：优先从**现有迁移脚本、实体类、或已有正式建表 SQL** 归纳；若仅有 JDBC URL 无 DDL，则基于引擎写**与当前生态一致的建议**，并注明「仓库内未见样例表结构，以下约束待首批迁移落地后修订」。
- **迁移与版本管理**：识别 Flyway/Liquibase/Prisma 等脚本位置与命名习惯。
- **安全与敏感数据**：若有加密字段、审计表、数据脱敏实现则摘要；否则简写。
- **其他最佳实践**：结合项目既有表（若有）中的 `created_at`、`deleted` 等模式总结。

完成分析后，按上文章节顺序写入 `sdd/数据库设计规范.md`。主文档以**一个主用引擎**为主撰写；若项目明确多引擎（如 Oracle + MySQL），在「适用数据库」中分段说明，避免把两套全文不加区分地堆叠。

---

## 阶段三：未检测到数据库时 — 只澄清，不生成

在无法可靠定位目标关系型数据库时：

1. **立即停止**，不创建、不写入 `sdd/数据库设计规范.md`。
2. 向用户发起澄清时，**禁止只抛裸问题**。每个待确认维度必须写成：
   - **一句话**说明要确认什么；
   - **选项**：**A、B、C、D…**（同一维度连续编号，通常 2～4 项）；每项附简短适用场景或得失；
   - **推荐项**：**恰好一项**标 **（推荐）** 或行末 **`本项推荐：X`**，勿矛盾；
   - **请用户**回复字母、「按全部推荐项」、或自定义。
   - 选项接近时仍须 **唯一推荐**，并一句话说明优先理由。
3. 澄清应覆盖的维度（每维 **A/B/C/D + 唯一推荐**；下列仅示意）：
   - **主用关系型引擎**（如 MySQL、PostgreSQL、Oracle、SQL Server、其他）。
   - **版本与部署**（自建、云 RDS、容器内版本区间等）。
   - **命名与字符集**（如库表字段 snake_case、UTF-8 / utf8mb4、排序规则等）。
   - **主键与外键策略**（自增 vs UUID、是否启用数据库级外键等）。
   - **软删除与审计字段**（是否统一 `deleted`/`is_deleted`、是否强制 `created_at`/`updated_at`）。
   - **迁移工具**（Flyway、Liquibase、Prisma、手工 SQL、首版未上等）。
   - **其他**（多租户、分库分表预期等，可选）。
4. **等待用户完整答复**后再进入 **阶段四**。未覆盖维度可追问「是否采纳推荐 **X**」，**不得在无确认时写入最终规范**。

若用户催促，重申须完成 **A/B/C/D + 推荐** 的澄清并得到确认。

### 澄清表述示例（结构示意）

```markdown
### 待您确认：主用数据库

- **需确认**：本项目关系型数据库类型。
- **选项**：
  - **A**（推荐）：MySQL 8.x / MariaDB 10.x — 与大量 Spring/Java 生态示例一致，运维资料多。
  - **B**：PostgreSQL — 约束与扩展丰富，适合复杂查询与分析型负载。
  - **C**：Oracle — 企业既有资产或采购约束常见。
  - **D**：其他（请注明产品与版本）。
- **本项推荐：A**
- **请您**：回复字母或说明自定义方案。
```

---

## 阶段四：按澄清生成基础规范（无现成库证据时）

仅在 **阶段三已得到用户答复** 后执行：

- 按上文相同章节顺序生成 `sdd/数据库设计规范.md`。
- 以用户选定的引擎为主撰写「数据类型」等方言相关小节。
- 无法从仓库验证的段落须标注「基于用户澄清，待库与迁移落地后核对」，**不得假装已通过 DDL 分析验证**。

---

## 写作与质量要求

- **单文件**：仅一个 `.md`，内部用标题层级组织。
- **可追溯**：配置/脚本推断处注明依据（如「根据 `application.yml` 中 `jdbc:postgresql`」）；澄清内容注明「根据用户说明」。
- **语言**：简体中文为主；数据库对象名、关键字、配置键保持业界常用英文。
- **简洁**：不必粘贴完整 `pom` 或 compose；类型与规则用列表归纳。

## 完成后

- 告知用户输出路径：`sdd/数据库设计规范.md`。
- 列出未决项（多数据源未选、澄清未完成等）如有。
