# 生成后端代码规范（单文件）

## 目标

- 在**当前工作区对应仓库根目录**下，生成 **一份合并后的 Markdown**：`sdd/后端代码规范.md`。
- **禁止**在未探测、未澄清前假定技术栈（不要用「默认 Spring Boot」等替代真实结论）。
- **禁止**依赖仓库外的示例目录或本技能正文未列出的外部文件路径；执行时**只**根据当前项目代码与用户澄清内容写作。
- 若 `sdd` 目录不存在则创建。

## 章节顺序（必须遵守）

顶层 `##` 标题按下列顺序输出（**主干**与标准「后端规范目录骨架」一致；**内容**可因项目删减，但顺序不变）：

1. **概述与使用说明**（各章对代码生成/协作的约束；标明本文档为单文件总册）
2. **技术栈**
3. **后端项目结构**
4. **后端模块命名规则**
5. **后端主要业务模块说明**（模块职责、边界；无现成模块则写规划或「待补充」并注明依据）
6. **分层结构**
7. **Controller层规范**
8. **Service层规范**
9. **数据访问层规范**
10. **数据传输**（DTO、Entity、VO 等命名与转换约定，合并于此章，勿单独拆文件）
11. **异常处理**
12. **日志记录**
13. **注释规范**
14. **常量类命名规范**
15. **持久层操作**（ORM、SQL、Mapper/Repository 约定等与项目实际一致的部分）
16. **分页操作**
17. **统一响应与核心对象**（如统一包装类、错误码约定、分页响应结构等；项目中若无则如实写「未使用」或按澄清填写）
18. **公共工具**（表格列出工具类；重要项用 `###` 写使用要点与禁止误用场景）
19. **公共技术组件**（如文件存储、调度、导入导出等；以仓库真实集成为准，表格 + 要点小节）
20. **公共接口**（内部/基础平台类接口约定与用法摘要；无则标注 N/A）
21. **说明**（维护原则、与项目内其他规范的衔接——可短）

章节内部可用 `###` 细分；不必为每章单独拆文件。

---

## 阶段一：探测是否存在后端项目

在仓库根目录及**合理子路径**中查找后端工程证据，**综合判断**，不要只看根目录单个文件。

### 应检查的线索（示例，可扩展）

- **构建与依赖**：`pom.xml`、`build.gradle`、`build.gradle.kts`、`go.mod`、`Cargo.toml`、`pyproject.toml`、`requirements.txt`（结合目录判断是否为服务端）、`*.csproj`、`composer.json`（PHP）等。
- **框架与入口**：Spring Boot 启动类、`application.yml`/`application.properties`、`main.go`、`manage.py`/`asgi.py`、`Program.cs`、`Nest` 入口等。
- **典型源码布局**：`src/main/java`、`internal/`、`app/`、`cmd/`、`services/` 等与语言习惯匹配的目录。

### 单体仓库 / 多服务

- 搜索 `services/*`、`server`、`api`、`backend`、`apps/*` 等常见目录下是否另有**独立构建文件**或多模块根 `pom.xml` / `go.work` 等。
- 若发现 **多个** 可能的后端根/服务：列出候选路径与依据，**请用户指定**针对哪一目录生成规范；**在用户选定前不要生成文档**。

### 判定结果

- **找到且唯一（或用户已选定）**：进入 **阶段二（分析并生成）**。
- **找不到**：进入 **阶段三（仅澄清，等待答复）**。**在此阶段不得创建或写入** `sdd/后端代码规范.md`。
- **仅有测试/示例子项目**：向用户确认是否以该子路径为规范对象；未确认前不生成。

---

## 阶段二：基于代码分析填写规范

在判定的后端根目录（或服务模块根）下：

- 从构建文件与锁文件（如有）整理**技术栈**：语言、框架、构建工具、Web/RPC、DB 与 ORM、缓存/消息、测试与质量工具等；**只写项目中真实存在的**，未使用的不编造。
- **后端项目结构 / 分层 / 命名**：根据实际包路径、模块划分、`controller`/`service`/`repository`/`mapper`/`domain` 等归纳；**仅当仓库中确实存在某约定时再写**，不抄虚构包名。
- **Controller / Service / 数据访问层 / 数据传输 / 异常 / 日志 / 注释 / 常量 / 持久层 / 分页**：从代码与配置中提炼模式（注解、事务、校验、分页参数、全局异常处理、日志框架配置等）。
- **统一响应与核心对象**：定位项目实际使用的响应包装、错误码枚举、分页结果类型等。
- **公共工具 / 技术组件 / 公共接口**：扫描 `util`、`common`、`shared`、`infrastructure` 及对外/feign/http 客户端封装；**每个重要项**在对应章用表格 + `###` 要点，**一律以当前仓库源码为准**。

完成分析后，按上文章节顺序写入 `sdd/后端代码规范.md`。

---

## 阶段三：未检测到后端时 — 只澄清，不生成

在无法可靠定位后端工程时：

1. **立即停止**，不创建、不写入 `sdd/后端代码规范.md`。
2. 向用户发起澄清时，**禁止只抛裸问题**。每个待确认维度必须写成：
   - **要确认什么**（一句话）；
   - **选项列表**：用 **A、B、C、D…** 依次编号（同一维度内连续字母，通常 2～4 项；必要时可到 E、F），每项一行，附简短适用场景或得失；
   - **推荐项**：在**恰好一项**选项旁标注 **（推荐）**，或在该维度末尾单独写一行 **`本项推荐：X`**，勿矛盾；
   - **请用户**回复字母组合、或「按全部推荐项」、或自定义方案。
   - 若选项优劣接近，**仍须指定唯一推荐字母**，并说明为何优先于次选。
3. 澄清应覆盖的维度（每维均须 **A/B/C/D… + 唯一推荐**；下列仅示意方向，勿当成用户已选定）：
   - **语言与运行时**（如 Java、Go、Node、Python、C# 等）。
   - **框架与构建**（如 Spring Boot、Micronaut、Gin、Echo、Nest、FastAPI、ASP.NET Core 等）。
   - **数据与持久化**（关系库 + JPA/MyBatis、GORM、SQL 手写比例等）。
   - **API 形态**（REST + JSON、RPC、GraphQL 等）。
   - **分层与模块习惯**（经典三层、DDD 骨架、按包按模块拆分等）。
   - **横切能力**（统一异常、日志、鉴权、校验、分页约定）。
   - **目录与 monorepo**（单服务、多模块 Maven、多 repo 聚合等）。
   - **公共工具/组件/内部接口**：首版是否纳入规范正文、或占位「待建设」等选项。
   - **其他约束**（可选）：同样 **A/B/C… + 推荐**。
4. **等待用户完整答复**（或用户明确表示「全部按推荐项」等）后，再进入 **阶段四**。未覆盖的维度可追问「是否采纳推荐 **X**」，**仍不得在无确认时写入最终规范**。

在用户催促时，应重申：需完成 **A/B/C/D + 推荐标注** 的澄清并得到确认后，才会生成文件。

### 澄清表述示例（结构示意）

```markdown
### 待您确认：后端框架

- **需确认**：本项目计划采用的后端框架与构建方式。
- **选项**：
  - **A**（推荐）：Spring Boot（Maven/Gradle）+ 典型三层 — 企业 Java 主流，生态与资料齐全。
  - **B**：Micronaut / Quarkus — 冷启动与原生镜像友好，适合云原生场景。
  - **C**：Go + 主流 Web 框架（如 Gin）— 部署简单、并发模型清晰。
  - **D**：其他（请说明语言与框架）。
- **本项推荐：A**
- **请您**：回复字母或自定义方案。
```

（选项旁 **（推荐）** 与 **本项推荐：X** 可同时用于可读性；若仅用一种，全文须统一、推荐字母唯一。）

---

## 阶段四：按澄清生成基础规范（无现成后端工程时）

仅在 **阶段三已得到用户答复** 后执行：

- 按上文相同章节顺序生成 `sdd/后端代码规范.md`。
- 内容以用户澄清为准；无法从仓库验证的段落须标注「基于用户澄清，待项目落地后核对」，**不得假装已通过代码分析验证**。

---

## 写作与质量要求

- **单文件**：全文一个 `.md`，内部用标题层级组织。
- **可追溯**：代码分析结论注明依据（如「根据 `pom.xml`」「根据 `…/controller`」）；澄清内容注明「根据用户说明」。
- **语言**：简体中文为主；类名、包名、配置键保持原文。
- **简洁**：技术栈用分类列表；勿整份粘贴依赖坐标。

---

## 完成后

- 告知用户输出路径：`sdd/后端代码规范.md`。
- 若存在未决项（多后端根未选、澄清未完成等），明确列出后续待办。
