# OpenSpec → 测试用例清单

根据 **`openspec/changes/<change>/`** 下已生成的工件（及用户指定的同目录补充文件），输出一份与仓库参考文档 **同结构** 的测试用例 Markdown。

**结构骨架速查**：[reference-template.md](reference-template.md)

---

## 输入范围（必读）

1. **定位变更目录**  
   - 用户给出 `<change>` 名称或 `openspec/changes/<change>` 路径；若未给出，可用 `openspec list` / `openspec instructions apply --change "<name>" --json` 解析 `contextFiles`，不得凭空捏造路径。

2. **优先读取的文件**（存在则全部阅读）  
   - `proposal.md`：范围、动机、成功标准  
   - `design.md`：流程、组件、接口、错误形态、边界  
   - `specs/**/*.md`：每条 `### Requirement:`、列表验收句、MUST/SHOULD、场景 bullet  
   - `tasks.md`：任务条可作为「实现已承诺能力」的覆盖清单  

3. **与实现对齐**  
   - 清单中的路由、组件路径、接口路径若工件未写清，标注「待补充」或「见代码」，**不得伪造具体路径**。  
   - 若 spec 与 design 冲突，在「备注」中写明采纳依据（优先可验收的 spec 场景）。

---

## 硬性规则

### 1）第一条用例必须是「登录 / 鉴权前置」

- **有前端登录流程**：`TC_{缩写}_001` 写 **成功登录**（账号密码或项目实际方式），前置条件为未登录；预期包含跳转落地与会话有效。  
- **纯后端、过滤器、SDK、无页面**：`TC_{缩写}_001` 写 **合法凭证访问**（如携带 token / 会话Cookie 调用首个业务接口成功），语义等价于「已进入可测状态」。  
- **变更完全不涉及需要登录的系统**（极少）：第一条仍为「环境就绪 + 访问入口可用」，并在备注说明为何无独立登录步骤。

### 2）尽可能覆盖全部操作性功能

从工件中系统抽取并映射到用例（无则省略并备注「本变更不涉及」）：

| 来源线索 | 典型用例方向 |
|----------|----------------|
| Requirement / 验收场景 | 每条 MUST + 关键场景至少一条正向或负向用例 |
| design 中的流程图、顺序 | 分支（取消、失败、重试）单独成条 |
| API / 页面字段 | 必填、格式、重复、边界值、组合查询 |
| 列表类 | 初始加载、单列查询、多条件 AND、重置、排序、分页首页/末页、size 边界 |
| 写操作 | 新增成功/校验失败、编辑回填与禁用规则、删除确认与取消 |
| 权限与安全 | 未登录、无权限、非法参数（若 spec 涉及） |
| 交互细节 | Loading、防抖、二次确认、幂等等（design/spec 提及则写） |

**覆盖率自检（生成后在文档外心智检查即可）**：tasks.md 中每条 `- [ ]`/`- [x]` 任务是否至少有一条用例可追溯到对应需求或场景；遗漏则补用例或在备注列出「待实现任务 XXX，暂不测」。

### 3）编号与命名

- 格式：`## TC_{模块缩写}_{三位序号} - {简短中文标题}`，例如 `TC_YGJCXX_001`。  
- **模块缩写**：来自 proposal 标题、变更 slug 或用户指定；**全篇唯一、大写**（4～8 字符为宜）。  
- 序号从 `001` 连续递增；**001 固定留给登录/鉴权前置**。  
- 「测试用例总数」与正文条数、统计表合计 **三者一致**。

### 4）单条用例正文字段（顺序固定）

每条必须包含且仅用以下五级标题下挂列表（与参考模板一致）：

- **功能名称**  
- **用例标题**  
- **前置条件**（编号列表）  
- **测试步骤**（编号列表，步骤可含子 bullet）  
- **预期结果**（编号列表，可验收、可观察）

条与条之间使用单独一行的 `---`。

---

## 输出位置与文件名

- 默认写入用户指定路径；若未指定：建议 `docs/` 或 `bak/_sdd/docs/<模块名>/`，文件名为 **`test_case.md`**。  
- 若用户只要对话内预览，先输出全文再询问是否落盘。

---

## 文末尾段（必须）

1. **测试用例统计**  
   - 「按功能分类统计」表：行 = 从本清单归纳的功能模块（登录、页面加载、查询、…），列含数量，最后一行总计。  
   - 「按测试类型分类统计」表：正向 / 异常 / 边界 / 权限 / 幂等 / UI 适配等，按实际归纳，总计与用例数一致。

2. **备注**  
   - 写明 OpenSpec 变更名、主要工件文件名；数据准备、环境变量、已知限制；spec 与实现待对齐项。

---

## 简要流程（执行顺序）

1. 解析变更目录与 `contextFiles`，读完 proposal / design / specs / tasks。  
2. 确定模块中文名、缩写、路由与接口（未知则占位）。  
3. 编写 `TC_*_001` 登录/鉴权前置用例。  
4. 按功能维度罗列其余用例，优先 **主流程 → 异常 → 边界 → 非功能（性能/响应式仅 spec 要求时）**。  
5. 填写模块信息与总数，生成两张统计表与备注。  
6. 自检：001 为登录类；编号连续；总数一致；每条有可执行步骤与可观察预期。
